# AI 商品图文内容生产与智能质检平台 MVP 开发规格

## 1. 文档目的

本文档用于将总体方案转化为可执行的第一阶段开发范围，作为产品设计、技术设计、任务拆分和验收的共同基线。

本次建设允许对原 `image_qa_mvp` 进行较大重构：不要求兼容原有页面、接口或本地任务状态，只复用已经验证有效的生成、OCR、审查和候选排序能力。

## 2. MVP目标

首期在 4—8 周内跑通一条可演示、可试用的商品图文生产链路：

```text
创建商品项目
→ 录入商品资料与参考图
→ 生成并调整多页内容规划
→ 选择生成配方与模板
→ 生成图片并完成文字排版
→ 自动质检、排序和修复
→ 人工确认并整套导出
→ 将有效方案保存为可复用配方
```

首期重点验证以下三件事：

1. 商品资料能否稳定转化为一套多页内容。
2. 生成、排版和质检能否形成闭环。
3. 验证有效的方法能否保存并在下一个商品项目中复用。
4. 同一套配方能否稳定应用于多个SKU，并对失败任务进行隔离和重试。

## 3. 首期假设

- 首期直接使用当前工作区已有的商品、品牌和测试资料，优先选择资料较完整的洗衣机、干衣机、洗烘套装及 X11 相关案例，但平台数据结构不与单一型号绑定。
- 首期同时支持单商品多页生产和多 SKU 批量生产。
- 首期先建设 3—5 个固定配置的核心页面模板，不开发可视化拖拽编辑器。
- 每个页面支持生成 1—3 张图片候选。
- 图片文字采用分层合成，不依赖图片模型生成最终小字和参数文字。
- 保留人工审核，不允许未经确认的配方自动发布。
- 默认采用 Azure OpenAI、Azure AI Vision 等现有模型服务。
- 首期产品以本地版本运行，项目数据、任务记录和生成文件均在本地持久化；模型调用仍通过服务端访问现有 Azure 资源。
- 默认采用全新的前后端架构，原 MVP Web Demo 仅作为能力参考。

## 4. MVP范围

### 4.1 必须完成（P0）

| 模块 | P0范围 |
|---|---|
| 项目与商品资料 | 创建项目、保存商品信息、上传参考图、填写品牌与输出要求 |
| 多SKU批量生产 | 批量录入或导入SKU、批量套用配方、查看进度、失败隔离重试和按SKU导出 |
| 内容策划 | 生成多页页面规划和文案，支持人工修改及确认 |
| 生成配方 | 选择已发布配方，绑定商品变量、模型、参数和模板 |
| 图片生产 | 支持文生图、参考图生成、商品替换或编辑，生成多候选 |
| 图文合成 | 支持 3—5 个模板，完成字体、字号、颜色、位置和安全区排版 |
| 智能质检 | 复用 OCR、参考一致性、区域漂移、候选评分和一轮重新生成修复 |
| 新增质检 | 增加文字遮挡、模板安全区、商品事实和基础多页一致性检查 |
| 审核与导出 | 查看候选及问题、选择结果、重新生成、确认页面、整套导出 |
| 配方管理 | Prompt版本、配方草稿/发布、示例结果和基础复用 |
| 任务与追踪 | 异步任务状态、错误重试、生成记录和质检记录 |

### 4.2 有余量再完成（P1）

- Prompt 原版与候选版的真实出图 A/B 对比；
- 多模型效果、成本和耗时对比；
- 模特及人物形象库；
- 更完整的品牌规范库；
- 配方标签、搜索和案例卡片展示；
- 人工评分和质量数据看板；
- 配方审批和回滚操作。

### 4.3 首期不做

- 3D模型、白模及工业设计渲染；
- 公开Prompt社区或交易市场；
- 通用Prompt编辑器；
- 复杂画布式专业设计工具；
- Chrome插件和独立桌面客户端；
- 完全无人审核的生产发布；
- 一次性适配所有家电品类；
- 完整DAM、PIM或企业级工作流系统。

## 5. 用户与权限

首期可先实现两类角色：

### 5.1 业务用户

- 创建和管理商品项目；
- 创建多SKU批量任务，查看各SKU生产状态；
- 填写商品资料并上传参考素材；
- 生成、调整和确认页面内容；
- 使用已发布配方；
- 查看质检问题并选择结果；
- 导出整套内容。

### 5.2 管理员/专家用户

- 管理Prompt版本和生成配方；
- 管理模板、模型参数和质检规则；
- 查看完整生成及质检记录；
- 测试并发布配方；
- 管理基础品牌资料和授权信息。

如果首期不接入正式身份系统，可使用简单角色切换，但数据模型和接口必须预留用户与权限字段。

## 7. 核心业务流程

### 7.1 创建项目

1. 用户创建商品项目。
2. 填写产品名称、品类、型号、卖点、参数和品牌信息。
3. 上传商品图、品牌参考图及其他参考素材。
4. 系统校验必填项、图片格式和不可修改事实。
5. 保存结构化商品档案。

### 7.2 内容策划

1. 系统根据商品档案生成建议页面结构。
2. 每页包含页面类型、表达目标、标题、正文、视觉要求和建议模板。
3. 用户可新增、删除、调整顺序和修改文案。
4. 用户确认后生成正式页面计划。

首期建议提供：主视觉页、核心卖点页、功能说明页、场景页和参数页。

### 7.3 配方选择与生成

1. 系统根据品类和页面类型推荐已发布配方。
2. 用户选择配方和模板，可调整少量业务参数。
3. 系统将商品档案及页面内容填入配方变量。
4. 后台异步生成 1—3 张候选图。
5. 图片生成和文字排版完成后进入质检。

### 7.4 质检与修复

1. Agent根据任务、参考图和页面计划生成审查计划。
2. OCR、参考图对比及平台规则提供审查证据。
3. 系统输出每张候选图的结论、问题、分数和修复建议。
4. 候选结果按质量排序。
5. 排版类问题由合成引擎重新排版。
6. 商品、人物或场景问题生成修复Prompt并重新生成一次。
7. 无法自动判断的内容标记为人工确认。

### 7.5 审核与交付

1. 用户选择每页最终结果。
2. 所有页面确认后生成整套预览。
3. 支持单页原图、合成图及整套图片导出。
4. 保存输入、输出、模型参数、Prompt版本和质检报告。

### 7.6 配方沉淀

1. 专家从效果良好的项目中创建配方候选版本。
2. 保存Prompt、变量、模型、参数、模板和示例结果。
3. 通过测试及人工确认后发布。
4. 新项目可以搜索或由系统推荐该配方。

### 7.7 多SKU批量生产

1. 用户创建批量任务，通过表格录入或CSV/XLSX导入多个SKU的基础信息。
2. 每个SKU分别绑定商品参考图和必要素材。
3. 用户为整批任务选择统一页面方案、配方和模板，也可以对单个SKU覆盖配置。
4. 系统为每个SKU创建独立生产子任务，并汇总展示总体进度。
5. 单个SKU失败不影响其他SKU继续执行，失败项可单独重试。
6. 完成审核后按SKU目录批量导出，并提供批次结果摘要。

## 8. 功能需求

### FR-01 项目与商品档案

- 项目支持草稿、生产中、审核中、已完成和已归档状态。
- 商品档案支持结构化字段及补充说明。
- 明确区分“已验证事实”和“生成建议”。
- 所有数字、单位、型号及认证信息默认属于不可自由改写内容。
- 参考图需记录用途，例如产品外观、局部结构、品牌风格或场景参考。

### FR-02 页面规划

- 根据商品档案生成多页计划。
- 每页必须包含唯一ID、顺序、页面类型、文案、视觉目标和状态。
- 文案支持一级至五级标签，但首期界面可只展示实际使用的层级。
- 用户修改内容后保留最新确认版本。

### FR-03 生成配方

- 配方由Prompt版本、变量定义、模型配置、模板和质检策略组成。
- 配方至少支持草稿、测试中、已发布、已停用状态。
- 生产任务只能使用已发布版本。
- 每次生成必须记录实际使用的配方及Prompt版本。

### FR-04 图片生成与编辑

- 支持文本生成图片、参考图生成及图片编辑。
- 支持1—3个候选结果。
- 支持配置尺寸、质量和参考图。
- 任务采用异步执行，前端可查看当前阶段和失败原因。
- 请求失败可按策略重试，但不能重复创建不可识别的任务。

### FR-05 图文分层与模板

- 原始底图和文字图层分别保存。
- 模板定义画布尺寸、文字区域、安全区、字体、字号、颜色和对齐方式。
- 文字修改后无需重新生成底图。
- 文本超出区域时必须提示或自动调整，不能静默裁切。
- 首期至少支持3—5个模板。

### FR-06 智能质检

复用现有MVP：

- Agent审查计划；
- OCR文字证据；
- 商品参考一致性；
- 目标及非目标区域变化；
- 基础版式稳定性；
- 多候选评分排序；
- 一轮重新生成修复。

首期新增：

- 文字框与商品主体遮挡；
- 模板安全区及页边距；
- 商品档案中的名称、数字、单位和参数校验；
- 同项目多页字体、颜色和模板一致性；
- 基础品牌禁用项和允许项检查。

### FR-07 审核与结果管理

- 用户可查看参考图、底图、合成图和问题标注。
- 支持选择候选、重新生成、重新排版和确认。
- 未处理的P0/P1问题不得标记为最终通过。
- 人工覆盖系统结论时需记录原因。

### FR-08 导出与归档

- 支持单页及整套导出。
- 输出至少包含最终合成图和项目摘要。
- 系统保留生成记录、Prompt版本、模型参数和质检报告。
- 失败或未确认内容不能混入正式交付包。

### FR-09 多SKU批量任务

- 支持手工新增SKU及CSV/XLSX批量导入，提供首期固定导入模板。
- 每个SKU拥有独立商品档案、页面计划、生成任务和质检结果。
- 支持整批应用配方、模板和页面计划，并允许单SKU覆盖。
- 批量任务显示总数、处理中、待审核、已完成和失败数量。
- 支持暂停后继续、仅重试失败SKU及查看单SKU错误信息。
- 批量导出按SKU隔离目录，未确认或失败的SKU不进入正式结果。

## 9. 核心数据对象

| 对象 | 主要内容 |
|---|---|
| `Project` | 单商品项目名称、用户、状态、品类、创建时间 |
| `Batch` | 批量任务名称、公共配置、总体状态和进度统计 |
| `BatchItem` | 批次内SKU、对应Project、覆盖配置、执行状态和错误信息 |
| `ProductProfile` | 商品事实、卖点、参数、品牌、渠道、限制信息 |
| `Asset` | 图片、字体或其他素材及其用途、来源、授权信息 |
| `PagePlan` | 多页内容规划及当前版本 |
| `PageItem` | 单页类型、文案、视觉目标、模板和状态 |
| `PromptAsset` | Prompt主体、变量定义、用途及来源 |
| `PromptVersion` | Prompt版本、变更说明和发布状态 |
| `Recipe` | Prompt版本、模型、参数、模板和质检策略 |
| `GenerationJob` | 任务输入、阶段、重试、耗时、错误和成本信息 |
| `Candidate` | 底图、合成图、所用参数及候选状态 |
| `QAResult` | 结论、分项问题、分数、证据及修复建议 |
| `ReviewDecision` | 人工选择、覆盖原因和确认时间 |

建议优先稳定这些对象的含义和关系，再开发具体页面。

## 10. 状态设计

### 项目状态

```text
draft → planned → producing → reviewing → completed → archived
```

### 页面状态

```text
draft → ready → generating → qa_review → approved
                           ↘ failed / needs_review
```

### 配方状态

```text
draft → testing → published → deprecated
```

### 批量任务状态

```text
draft → ready → running → needs_review → completed
                    ↘ partial_failed / paused
```

状态转换必须由后端控制，前端不能直接写入任意终态。

## 11. 技术架构建议

首期以本地可运行、后续可替换为云端组件为原则。考虑现有核心模块为Python，推荐采用以下结构：

- 前端：React/TypeScript单页应用；
- 后端：Python FastAPI；
- 异步任务：本地独立Worker，任务状态持久化；
- 数据库：首期SQLite，数据访问层保留切换PostgreSQL的能力；
- 文件存储：本地受控数据目录，统一通过存储接口读写；
- 队列：首期可使用数据库任务表或本地Redis，按并发需要选择；
- 模型服务：Azure OpenAI、Azure AI Vision；
- 密钥管理：仅使用服务端本地环境变量，不写入浏览器或数据库；
- 可观测性：结构化日志、任务Trace和模型调用记录。

首期使用单体后端加独立Worker，不提前拆分微服务。模型、数据库、文件存储和任务队列均通过适配接口接入，以便后续迁移至PostgreSQL、Azure Blob Storage和Service Bus。

## 12. 原MVP处理策略

### 12.1 建议复用

- `image_generation.py`：图片生成和编辑调用逻辑；
- `azure_vision_ocr.py`：OCR适配；
- `review_planner.py`、`review_requirements.py`：审查计划；
- `llm_reviewer.py`：多模态审查及结构化结果；
- `visual_review.py`、`target_localization.py`：视觉证据和目标区域；
- `agent_workflow.py`：候选评分、排序和一轮修复逻辑；
- 现有测试、示例和历史生成结果。

复用前应将模型调用、业务规则和任务状态从Web层中拆出，改造成独立应用服务或领域服务。

### 12.2 建议重建

- 现有 `web/index.html`；
- `web_demo.py` 中的页面服务和临时任务状态；
- 以文件路径为中心的数据管理方式；
- 缺少持久化和权限的本地工作流；
- 与单个美的演示案例耦合的默认配置。

不要求保留原Web API兼容性。历史结果只作为测试数据和案例素材，不做正式数据迁移。

## 13. API边界建议

首期接口可按资源划分：

```text
/projects                 项目
/projects/{id}/profile    商品档案
/projects/{id}/plan       页面规划
/projects/{id}/pages      页面及状态
/batches                  批量任务
/batches/{id}/items       批次内SKU和执行状态
/recipes                  配方库
/prompt-assets            Prompt及版本
/generation-jobs          图片生成和合成任务
/qa-jobs                  质检任务
/candidates               候选结果
/reviews                  人工审核
/exports                  导出任务
/assets                   素材上传与查询
```

生成、OCR、质检和导出均采用异步任务接口。创建任务后返回任务ID，前端通过轮询或事件通道获取进度。

## 14. 非功能要求

### 14.1 可追溯性

- 每张结果必须能追溯到商品档案、页面、配方、Prompt版本、模型和参数。
- 所有人工覆盖和配方发布操作保留记录。

### 14.2 安全

- API密钥不得暴露在浏览器端。
- 上传文件需要类型和大小校验。
- 不同项目的素材和结果必须隔离。
- Prompt、图片、字体和模特素材记录来源及授权状态。

### 14.3 稳定性

- 外部模型请求支持超时、限流和重试。
- 异步任务失败后可诊断、可重试，不重复污染正式结果。
- 长任务刷新页面后仍可恢复查看。

### 14.4 可评估性

- 记录生成耗时、模型参数、调用成本、QA分数和人工结论。
- 支持使用固定样本进行Prompt和模型回归测试。

## 15. 验收标准

### 15.1 端到端验收

- 可完成“建项目—填资料—生成计划—生产多页—质检—修复—审核—导出”完整流程。
- 可在新项目中复用至少一套已发布配方。
- 刷新页面或服务重启后，项目和任务记录仍然存在。

### 15.2 内容生产验收

- 一个项目可生成不少于3种页面类型。
- 每页可生成1—3张候选并选择最终结果。
- 至少3个模板能够完成图文分层合成。
- 修改文字后可重新排版而不重新生成底图。

### 15.3 质检验收

- 每个审查要求均有独立结论和证据。
- 能发现文字缺失/错误、明显商品偏差、非目标区域漂移和模板越界。
- 能区分确定性排版修复与重新生成修复。
- P0/P1问题未处理时不能进入正式导出。
- 可执行一次自动重新生成，并保留修复前后的结果。

### 15.4 配方验收

- 配方包含Prompt版本、变量、模型、参数、模板和质检策略。
- 只有已发布配方可被业务项目使用。
- 能从已完成项目创建配方候选，并在另一个项目中复用。

### 15.5 多SKU验收

- 可通过固定CSV/XLSX模板一次导入不少于5个SKU。
- 可为整批SKU应用相同配方、模板和页面计划。
- 可对单个SKU修改商品资料或覆盖配方配置。
- 单个SKU执行失败时，其他SKU能够继续完成。
- 可仅重试失败SKU，不重复执行已完成任务。
- 批量任务能够正确汇总进度，并按SKU输出独立目录和批次摘要。

### 15.6 建议验证数据集

- 至少10个代表性页面任务；
- 覆盖主视觉、卖点、场景、参数及商品替换；
- 同时包含通过样本和已知失败样本；
- 使用现有X11、Task2结果和MVP样例作为首批数据。

## 16. 测试策略

- 单元测试：数据对象、状态转换、模板布局、质检规则和评分逻辑；
- 集成测试：模型调用、OCR、对象存储、数据库及异步任务；
- 端到端测试：单商品从创建项目到整套导出，以及多SKU批量导入、执行、失败重试和导出；
- 回归评测：固定输入、Prompt版本、模型参数及期望结论；
- 人工评测：商品一致性、视觉质量、品牌风格和最终可用性。

现有 `image_qa_mvp/tests` 应保留为算法能力回归基础，但需要新增平台服务、数据持久化和完整流程测试。

## 17. 建设阶段

| 阶段 | 主要工作 | 预计范围 |
|---|---|---|
| 阶段一：基础架构 | 新前后端骨架、本地数据库、文件存储、任务队列、项目和素材 | 约1周 |
| 阶段二：策划与配方 | 商品档案、页面规划、Prompt变量和配方执行 | 约1—2周 |
| 阶段三：生产与合成 | 接入生图能力、候选管理、3—5个模板和文字排版 | 约1—2周 |
| 阶段四：质检与批量生产 | 重构现有QA、增加规则、修复、多SKU调度、审核及导出 | 约1—2周 |
| 阶段五：配方沉淀与验收 | 配方发布复用、回归集、试运行和问题修复 | 约1周 |

各阶段可以部分并行，最终周期取决于前端设计、部署环境和模型资源是否提前准备完成。

## 18. 已确认决策与剩余事项

### 18.1 已确认

1. 首期使用当前工作区已有的商品、品牌和测试资料开展验证。
2. 首期先建设本地运行版本，模型服务仍调用现有Azure资源。
3. 首期采用固定模板配置，不开发可视化拖拽编辑器。
4. 多SKU批量生产纳入P0。

### 18.2 剩余事项

以下事项不阻塞基础架构启动，可在对应模块开始前确认：

1. 首期是否接入正式登录；默认先采用简化角色切换。
2. 首批3—5个模板及页面类型的最终选择；默认从主视觉、卖点、功能、场景和参数页中选择。
3. Prompt Optimizer是否需要作为独立工具接入；默认仅参考其设计并在平台内独立实现相关能力。
