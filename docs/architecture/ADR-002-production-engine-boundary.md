# ADR-002：生产引擎作为深模块边界

## 状态

已采用。

## 决策

应用层只通过 `PageProductionEngine` 执行单页生产和仅重排。Prompt变量绑定、底图生成、商品分层、文字分层、模板布局、质检、一轮修复和候选排序都封装在该边界后。

底图生成通过 `BaseImageGenerator` 切换本地确定性实现与平台自有 Azure 适配器；持久化和导出分别通过 `ProductionRepository` 与 `ArchiveExporter` 隔离。

生活场景配方默认采用 `layered_product`：图片模型只生成无商品、无文字的环境底图，模板分别定义文字留白区、商品视觉锚点和允许延展区；引擎再从用户参考图提取商品，以独立透明图层合成，最后由确定性文字层排版。需要让模型直接编辑参考图时仍可显式选择 `model_edit`。两种策略、实际尺寸、质量、图层文件及商品框都写入候选元数据和导出包，不能靠审查模型猜测来源。

模型调用集中在 `integrations` 模块，OCR、审查计划、多模态审查、规则、评分和修复集中在 `quality` 模块。二者都属于当前工程，不从工作区外加载代码。

## 原因

这个接口让前端、任务编排和领域状态不需要知道 Azure、Pillow 或 OCR 的调用细节。替换模型、存储或质检算法时，上层流程和接口保持稳定。

## 影响

- 本地离线模式可以覆盖完整业务流程，不需要模拟前端结果。
- Azure模式只替换生成适配器，仍使用同一任务、质检、审核和导出流程。
- `layered_product` 保留参考商品像素并消除模型重复商品；其代价是本地抠图更适合背景干净的商品素材，复杂背景应先提供透明 PNG 或改用专业抠图服务。
- 当前工程不依赖原 MVP 包、目录、Web 演示状态或接口；删除旧目录不会影响启动和本地测试。
