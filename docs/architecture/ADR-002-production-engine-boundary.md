# ADR-002：生产引擎作为深模块边界

## 状态

已采用。

## 决策

应用层只通过 `PageProductionEngine` 执行单页生产和仅重排。Prompt变量绑定、参考图生成/编辑、文字分层、模板布局、质检、一轮修复和候选排序都封装在该边界后。

底图生成通过 `BaseImageGenerator` 切换本地确定性实现与平台自有 Azure 适配器；持久化和导出分别通过 `ProductionRepository` 与 `ArchiveExporter` 隔离。

生活场景配方默认采用 `model_edit`：应用层按“商品外观 → 局部细节”的顺序收集同一商品的多张参考图，图片适配器以高输入保真度一次发送给模型，由模型直接生成商品、可选新角度、环境效果与完整场景。模板定义文字留白区、商品视觉锚点和允许延展区；商品框是构图目标，不是事后贴图坐标。引擎最后只对营销文字做确定性排版。

`layered_product` 仅作为兼容模式保留，用于确实要求参考商品像素级不变的旧任务。两种策略、实际尺寸、质量、参考图列表、是否由模型生成商品、图层文件及商品目标框都写入候选元数据和导出包，不能靠审查模型猜测来源。

模型调用集中在 `integrations` 模块，OCR、审查计划、多模态审查、规则、评分和修复集中在 `quality` 模块。二者都属于当前工程，不从工作区外加载代码。

## 原因

这个接口让前端、任务编排和领域状态不需要知道 Azure、Pillow 或 OCR 的调用细节。替换模型、存储或质检算法时，上层流程和接口保持稳定。

## 影响

- 本地离线模式可以覆盖完整业务流程，不需要模拟前端结果。
- Azure模式只替换生成适配器，仍使用同一任务、质检、审核和导出流程。
- `model_edit` 能综合多角度和局部参考生成新的商品视角与场景光影，但不承诺逐像素复刻；审查需综合全部参考图判断商品身份和关键结构。
- `layered_product` 保留参考商品像素并消除模型重绘风险，但无法生成真实的新角度或让环境效果作用于商品，因此不再作为默认正式方案。
- 当前工程不依赖原 MVP 包、目录、Web 演示状态或接口；删除旧目录不会影响启动和本地测试。
